# Metrics Reference

Every metric below is exposed at `/metrics` (Prometheus text format) by the
service that owns it, and the business-facing ones (latency, precision/recall,
throughput, drift) are also persisted to ClickHouse so they survive restarts
and can be queried historically from the dashboard.

## 1. Latency

| Metric | Source | Definition |
|---|---|---|
| `ingestion_ws_to_kafka_ms` | ingestion | time from WS frame receipt to Kafka produce ack |
| `feature_window_emit_lag_ms` | feature-service | `now - window_end` at the moment a feature event is produced |
| `ml_inference_ms` | ml-inference | time from Kafka feature-event consume to alert produce (ensemble scoring + explanation) |
| `latency_ingest_to_alert_ms` | ml-inference (in `alerts` payload) | `alert.ts - feature.window_start` — **headline end-to-end metric**, see docs/data-contracts.md for why `window_start` rather than the raw event's own timestamp |

**Known, bounded latency spike:** the Isolation Forest / autoencoder are
periodically batch-retrained (every `retrain_every_n_windows` windows, see
`app/config.py`), and the one `process()` call that triggers a retrain takes
as long as that retrain does — measured ~500-900ms locally, well above the
steady-state p50 (~1-2ms). `pipeline.process()` runs on a single dedicated
executor thread (`app/main.py`), not inline on the asyncio event loop, so a
retrain stalls only that one message's own latency, not Kafka consumption,
`/health`, `/metrics`, or the other background loops. The 50ms p99 target in
`ARCHITECTURE.md` describes steady-state scoring, not retrain windows —
noted as a known, accepted tradeoff rather than hidden in the average.

All four are recorded as Prometheus histograms; p50/p95/p99 are what the
dashboard's "System Metrics" panel plots. Targets are in `ARCHITECTURE.md`
("Latency budget").

## 2. Detection quality

Computed against `data-generator`'s injected `scenario_label` ground truth
(see `services/data-generator/app/scenarios.py`), which is never sent to
`ml-inference` — only used by `tests/eval` to score predictions after the
fact. This is the same discipline as held-out labels in an offline eval set;
it's what makes "precision/recall" here a real number instead of a vibe.

| Metric | Definition |
|---|---|
| `precision` | alerts where `scenario_label != null` at that entity/window ÷ all alerts raised |
| `recall` | windows with `scenario_label != null` that produced an alert ÷ all such windows |
| `f1` | harmonic mean of precision/recall |
| `false_positive_rate` | alerts on normal (unlabeled) windows ÷ all normal windows |
| `mean_detection_delay_s` | time from scenario injection start to first alert for that entity |

Reported per scenario type (`volatility_spike`, `fraud_pattern`,
`latency_incident`, `data_corruption`, `regime_change`, `volume_spike`) and
in aggregate. Regenerated by `tests/eval/run_eval.py`, latest run committed to
`docs/benchmarks/latest.json` and rendered below by `scripts/render_metrics.py`.

## 3. Throughput / resource cost

| Metric | Source |
|---|---|
| `events_per_second` | ingestion, feature-service, ml-inference — each stage's Kafka consume rate |
| `process_cpu_seconds_total`, `process_resident_memory_bytes` | every service, via `prometheus_client` / `metrics-rs` process collectors |
| `kafka_consumer_lag` | per topic/partition, scraped from Redpanda's Prometheus exporter — the earliest signal that a stage can't keep up |

## 4. Model quality over time / drift

| Metric | Definition |
|---|---|
| `psi_by_feature` | Population Stability Index between the training baseline distribution and a trailing window of live feature values, per feature. PSI > 0.2 = significant drift (standard industry cutoff). |
| `ks_stat_by_feature` | two-sample Kolmogorov–Smirnov statistic, same comparison, more sensitive to shape changes PSI's binning can miss. |
| `drift_detected` | `true` if any feature's PSI > 0.2 or KS p-value < 0.01 |
| `precision`/`recall`/`f1` before vs. after an injected drift scenario | `tests/eval` runs the same scenario suite before and after `scripts/inject_drift.py` shifts the generator's underlying distributions, so degradation is a measured before/after delta, not a claim. |

## Severity thresholds (defaults, `services/ml-inference/app/rules.yaml`)

| `anomaly_score` | severity | action |
|---|---|---|
| < 0.55 | — | none |
| 0.55–0.75 | `watch` | `watch` |
| 0.75–0.90 | `alert` | `alert` |
| ≥ 0.90 | `critical` | `block` |

Overridable per-domain (`market` / `payments`) without a code change — see
the rules engine section of `ARCHITECTURE.md`.

## Latest measured numbers

Populated by `scripts/load_test.py` and `tests/eval/run_eval.py` once the
pipeline is running end-to-end; see `docs/benchmarks/latest.json` for the raw
output and the root `README.md` for the human-readable summary table.
